## 修

| 问题 | 为什么会影响演示 | 必须修改/已固定的处理 |
|---|---|---|
| “清除 / 重置”双口径 | 前端、后端与演示人员会把同一操作理解为不同命令 | 已固定：UI 文案为“重置”，唯一协议映射为 `command=reinit`。 |
| `execute success` 被误作完成 | 会提前读取旧文件或半成品，或把重置命令成功误作重置完成 | 已固定：`execute success` 只表示命令执行成功；启动路径继续等 `case complete`，重置路径继续等 `reinit complete`。 |
| 参考样本形状被误写为正式限制 | 后续真实后端可能输出非 20×20 热力矩阵或非 20 条 KPI 样本，前端会错误拒绝合法数据 | 已固定：热力图为动态 `Nx × Ny` 非空矩形矩阵，KPI 为动态 `N` 个有限样本；当前 20×20/20×1 仅是参考样本证据。 |
| `reinit` 成功口径不清 | 前端可能一直等待后端回 `command=init,status=""`，导致按钮和数据移除状态卡住 | 已固定：`status="reinit complete"` 即重置完成；前端据此移除 Calibrated 数据并恢复登录时按钮状态。 |
| `execute fail` 后续终态不清 | 前端可能继续等待 `case complete` / `reinit complete`，导致界面卡在等待态 | 已固定：`execute fail` 是命令失败终态；前端显示执行命令失败，后端本轮不再写完成终态。 |
| 六文件同批与新鲜度口径 | 只靠 `case complete` 字面量时，前端可能读到旧文件或半写完文件 | 已固定：后端完整写完并关闭六个 Calibrated 文件后，最后写 `status=case complete`；前端只在本轮启动后的 `execute success -> case complete` 链路上读取。 |
| 命令交互容易被过度设计 | 自动超时、取消、队列、恢复会放大演示复杂度 | 已固定：启动/重置互斥；不做取消、队列、自动超时、自动重试；失败解除按钮，刷新后一切回 Initial。 |
| 控制文件接口口径分散 | 前端可能不知道启动、重置和截图清零应走哪个接口 | 已固定：控制文件读写归一为 `GET /api/case2/control-file` 与 `POST /api/case2/control-file`。 |
| 截图触发与保存责任不清 | 若 Web 同时看 status 和 flag，会形成双重判断；若未落盘即清零，会丢截图；若固定 latest 会覆盖多次截图 | 已固定：Web 发现 `save_picture_flag` 从 `0` 到 `1` 即截图，Base64 传给适配服务；适配服务保存递增序号 PNG 后才清零。 |
| 静态原型中的数字/代表热图易被沿用 | 会把 40%、50% 或代表层当成运行时结果 | 已固定：CDF、均值、降幅由当前 KPI 样本派生；正式热图运行时绘制。 |

## 跳

| 项目 | 为什么跳过 | 风险/边界 |
|---|---|---|
| 命令取消、命令队列、自动重试 | 不支撑当前内部演示主线 | 若 Gate 5 真实环境证明需要，再单独升级；当前不进入 v1。 |
| 命令超时秒数、重连退避 | 用户已确认超时不考虑；刷新页面一切回 Initial | Gate 3 只需实现基本轮询，不引入自动超时状态机。 |
| 真实后端 manifest、批次 ID、原子目录切换 | P0-1 已按极简规则确认，不把更复杂发布机制强加给真实后端 | 若 Gate 5 证明共享目录读写不稳，再升级发布机制。本地打桩见 `realback_no.md`，与真实后端共用 flat 写完六文件再写状态。 |
| AOA/ZOA 与 `without dt` | 不驱动当前可见 UI 或演示主线 | 不得作为“未来兼容”字段混入 case2 正式结果批次。 |
