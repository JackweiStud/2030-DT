## 今天遇到了什么问题

一共 **3 类问题**，表面报错不同，根因有重叠：


| 现象                                        | 发生位置                                          |
| ----------------------------------------- | --------------------------------------------- |
| `'CASE2_SHARED_DIR' is not recognized...` | `dev-web-server.bat` 起的适配服务、以及 `back` 打桩      |
| `'vite' is not recognized...`             | `dev-web-server.bat` 起的 Web                   |
| 打桩进程秒退、无日志（修复过程中）                         | `back/case2/scripts/run.mjs` 第一版用 `import` 加载 |


另外，我在调试时曾误加 `server/node_modules` 检查——适配服务无 npm 依赖，该目录本就不存在，属于过度防御，已去掉。

---

## 根源原因

**核心不在 bat/ps1，而在** `package.json` **的 npm scripts 用了 bash 专用语法。**

macOS 上 npm 默认用 `sh`/`bash` 执行 scripts，所以这类写法能跑：

```json
"start": "CASE2_SHARED_DIR=\"${CASE2_SHARED_DIR:-$(cd ../comdatafiles && pwd)}\" node ..."
```

Windows 上 npm 默认用 **cmd.exe**，不认识 `${VAR:-default}`、`$(...)`、行首 `VAR=value command`，会把 `CASE2_SHARED_DIR=...` 当成要执行的命令名，于是报错。

架构上是这样的：

```
dev-web-server.sh / .bat+.ps1   ← 编排层（macOS 已验证 / Windows 今天首次验证）
        ↓ 调用 npm start / npm run dev
server/back package.json scripts ← 真正跨平台边界（之前只按 bash 写）
        ↓
node 进程
```

`dev-web-server.bat` / `.ps1` 本身逻辑没问题（会设置 `CASE2_SHARED_DIR` 再调 `npm start`），但 **子进程的 npm script 在 Windows 上先于 Node 就失败了**。

`vite` 找不到则是 **首次拉库未装依赖**：`node_modules/.bin/vite` 不存在，与脚本语法无关。

---



## 怎么解决的

1. `server/scripts/run.mjs`
  用 Node 解析默认共享目录（`path.resolve`），再启动适配服务；若 shell 已 `export DT_SHARED_DIR`，则尊重已有值。`CASE2_SHARED_DIR` 仅作为旧脚本 fallback。
2. `back/case2/scripts/run.mjs`
  同样处理环境变量默认值；用 `spawn` **启动** `case2-stub.mjs`（不能直接 `import`，因为 stub 入口有 `process.argv[1] === fileURLToPath(import.meta.url)` 判断，import 时不会跑 `main()`）。
3. `dev-web-server.ps1`
  启动前检查 `web/node_modules` 是否存在，缺依赖时给出 `npm install` 提示。
4. **本地**
  在 `code/web` 执行了 `npm install`。

## 上库后对 macOS / sh 的影响

**预期无负面影响**，反而更稳：


| 组件                                       | 是否改动          | macOS 影响                                                         |
| ---------------------------------------- | ------------- | ---------------------------------------------------------------- |
| `dev-web-server.sh`                      | 未改            | 无                                                                |
| `e2e-case2-stack.sh`                     | 未改            | 无                                                                |
| `server` / `back/case2` 的 `package.json` | 改为调 `run.mjs` | sh 会 `export DT_SHARED_DIR`，`run.mjs` 只在**未设置时**填默认值；旧 `CASE2_SHARED_DIR` 仍可 fallback |

macOS 上建议回归测一遍：`./code/scripts/dev-web-server.sh`、`cd code/back && npm start`、以及 `npm test` / e2e（如有 CI）。

## 后续双平台开发注意事项

**1. 不要把 shell 语法写进** `package.json` **scripts**

禁止在 npm scripts 里用：

- `VAR=value command`（Unix 行内环境变量）
- `${VAR:-default}`、`$(cd ... && pwd)`
- `&&` / `||` 依赖 shell 语义（Windows cmd 行为不同）

**2. 职责分层**

```
sh / ps1 / bat     → 路径解析、多进程编排、export 环境变量
package.json       → 只写平台无关的 node 命令
scripts/*.mjs      → 默认值、路径 resolve、可选参数（--dev、--no-picture）
业务 .mjs          → 只读 process.env，不假设由哪种 shell 启动
```

**3. 路径一律在 Node 里** `path.resolve`

不要用 `$(cd ../comdatafiles && pwd)`；Windows 盘符、反斜杠都交给 Node 处理。

**4. 注意「直接执行 vs 被 import」的入口守卫**

若业务文件有：

```js
if (process.argv[1] === fileURLToPath(import.meta.url)) { main(); }
```

wrapper 应 **spawn 子进程**，不要 `import` 该文件。

**5. 首次克隆文档写清楚**

Windows / macOS 共同前提：`cd code/web && npm install`（server/back 若无依赖可省略）。

**6. 新增脚本时的验证清单**

- [ ] macOS：`dev-web-server.sh` 能起 Web + adapter
- [ ] Windows：`dev-web-server.bat` 同上
- [ ] 单独 `npm start`（不经过编排脚本）两平台都能跑
- [ ] 环境变量覆盖：`DT_SHARED_DIR=... npm start` 生效；旧 `CASE2_SHARED_DIR=... npm start` fallback 仍生效
- [ ] 全新 clone（无 `node_modules`）是否有明确报错

**7. bat/ps1 与 sh 保持「对等」，但别重复 bash 逻辑**

Windows 侧 `dev-web-server.ps1` 已与 `.sh` 对齐；跨平台默认值应集中在 **Node wrapper**，避免三处各写一套默认路径。

---

**一句话总结**：macOS 上 sh 一直正常，是因为 bash 语法被 npm 间接执行了；Windows 上 bat 只是触发了同一条 npm script，暴露的是 `package.json` **未跨平台**。修法是把 shell 专属逻辑下沉到 Node wrapper，让 sh/bat 只负责编排，这样两平台共用同一套 npm 入口。
